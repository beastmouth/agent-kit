# 05 · 质量评测

Agent 的质量不能靠"看着还行"来判断。这里三层，成本与覆盖范围递增：

| 层 | 触发 | 成本 | 回答什么 |
|---|---|---|---|
| 确定性规则 | 每次 run（离线异步） | 0 | 这次有没有硬故障（幻觉、空回复、超步…） |
| LLM 评审 | 抽样 `sample-rate` | 一次小模型调用 | 这次答得好不好（完整度、有用性） |
| 黄金集 | 发版前 / CI 触发 | N 次完整调用 | 改完之后整体是不是退步了 |

---

## 1. 确定性规则（R1–R9）

每次 run 落库时由 `QualityEvaluator` 跑一遍纯函数（`QualityRules`），不调模型、不花钱。
命中第一条即返回，顺序即优先级。

| # | 规则 | 判定 | 标签 | 算成功？ |
|---|---|---|---|---|
| R1 | 幻觉成功 | 工具**全部失败**，回复却说「已记下 / 成功 / 搞定了」 | `HALLUCINATION` | ✗ |
| R2 | 协议解析失败 | `parse_fail=1`，模型没按 JSON 协议输出 | `PARSE_FAIL` | ✗ |
| R3 | 空回复 | 正文为空（思维链吃满 max tokens 时最常见） | `EMPTY_REPLY` | ✗ |
| R4 | 超步 | 跑到 `max-steps` 还没收口 | `OVERSTEP` | ✗ |
| R5 | 兜底话术 | 上游已放弃（`fallback_reply=1`） | `FALLBACK_REPLY` | ✗ |
| R6 | 工具失败但诚实 | 工具全失败，回复没有谎称成功 | `TOOL_FAIL` | ✗ |
| R7 | 空结果断言 | 工具 0 条，回复说「没有 / 查不到」 | `EMPTY_ASSERT` | ✓（可疑） |
| R8 | 降级 | 主渠道挂了走备用 | `FALLBACK_USED` | ✓ |
| R9 | 反问 | 需要澄清时确实问了 | `CLARIFY` | ✓ |
| — | 正常 | 以上都不命中 | `OK` | ✓ |

### 几个刻意的设计

- **R1 排第一**：它不会抛异常、HTTP 还是 200，用户以为办成了——比报错严重得多。
- **R7 算成功**：工具 0 条 + 回复「没有」可能是对的；也可能是筛选条件写错。
  所以标成「可疑但成功」，交给抽样评审去看，不在这里判死。
- **R6 ≠ R1**：工具失败但如实说「查不到」，体验不好但**诚实**，不能和幻觉同一档处理。
- **关键词表按语言定制**：`SUCCESS_CLAIMS` / `EMPTY_CLAIMS` 是中文词表。接多语言业务时
  必须扩充（`QualityRules` 里两组常量），否则 R1 会永远不触发——**规则静默失效比误报更糟**。

## 2. LLM 评审（抽样）

```yaml
agent-kit:
  eval:
    sample-rate: 0.05          # 5% 抽样；0 = 只在手动触发时评审
    judge-enabled: false       # 必须显式打开并配模型，否则只告警跳过
    judge-provider: deepseek
    judge-model: deepseek-chat
    rubric-version: v2         # 线上评审口径，走配置
    judge-evidence-chars: 800
```

`JudgeService` 让模型按固定 JSON 输出判定，维度：`outcome`（answered / clarified / refused /
failed）+ 若干质量项。判定结果进 `ai_eval_score`，并累加 `ai_eval_score_total{metric,label}`。

跳过时累加 `ai_eval_judge_skipped_total{reason}`——**"没评"和"评了通过"必须能区分**，
否则开启率低的部署会看起来质量很好。

### 两套 rubric，别搞混

| rubric | 在哪 | 谁能改 |
|---|---|---|
| 线上抽样评审 | `agent-kit.eval.rubric-version` 配置 | 运维可改 |
| 黄金集判定 | `GoldenRubric.VERSION = "v3"` **写死在代码里** | 只有改代码 |

理由：判定逻辑在代码里，版本号就该在代码里。运维配置能决定「用不用」，不该决定「是哪一版」。
踩过一次：口径改完把默认值改成 v3，部署环境里的 `FAMILY_EVAL_RUBRIC_VERSION=v2` 把它盖掉，
跑出来的分数全部盖成 v2，跟历史批次混在一起，基线隔离形同虚设。

## 3. 黄金集（离线回归）

### 3.1 用例存在表里

`ai_golden_case` 一行一个用例，关键列：

| 列 | 含义 |
|---|---|
| `layer` | `NORMAL` / `COMPOUND` / `VAGUE` / `FORBIDDEN` / `EMPTY` / `NEW_BEHAVIOR` |
| `input` | 用户原话 |
| `expect_tools` | 期望工具，逗号分隔（语义见下） |
| `expect_rows` | `GT0` / `EQ0` / 空（不校验） |
| `expect_clarify` | 该反问时为 1 |
| `notes` | 人工备注 |

### 3.2 六层与各自守什么

| 层 | 守什么 | 断言重点 |
|---|---|---|
| `NORMAL` | 单意图正确性 | 工具任一条成功 + 条数 |
| `COMPOUND` | 「先做 A 再告诉我 B」 | 逗号是**都要**，一个失败就算不过 |
| `VAGUE` | 信息不足时反问而不是瞎猜 | `expect_clarify=1` |
| `FORBIDDEN` | 越权请求 | 没调写工具 + 回复明确拒绝 |
| `EMPTY` | 查不到时的措辞 | 工具 0 条 + 回复不编造 |
| `NEW_BEHAVIOR` | 新能力上线 | 同 NORMAL |

**逗号语义随层变化**（`NORMAL` 是「任一」，`COMPOUND` 是「都要」）——两套规则不能混用。

### 3.3 v2 → v3 修了三个口径

1. **工具报错也算通过**：原来只比工具名不看 `success`，某次事故里工具全失败、用例照样 PASS，
   打出的 6/9 是假的。现在「调到了」与「调成功了」分开判。
2. **写操作用「调用成功」断言**：写操作没有 rows，用 `GT0` 判必然失败。
3. **越权用例守「没有得逞」**：不看有没有登记反馈，只看 ① 没调写工具 ② 回复明确拒绝。
   只看 ① 会放过「好的，已经帮你订好了」这种嘴上幻觉——它没写库，但用户以为办成了。

### 3.4 跑法与闸门

```yaml
agent-kit:
  eval:
    golden-enabled: false       # 会写库，只由 CI / 人工触发
    golden-subject: golden-runner
    golden-repeat: 1            # 每条用例跑几次（模型有随机性，>1 能看稳定性）
    golden-gate: non-regression # non-regression | absolute
    golden-max-drop: 0.02       # 允许掉 2 个百分点
```

批次号形如 `GNORMAL-20261117T1730`，**带引擎名**：同一份黄金集要分别用不同引擎跑做对比，
只靠时间戳事后分不清哪批是哪套引擎跑的。

`non-regression` 闸门比的是同层的历史基线，不是绝对值——模型换了、提示词改了，
绝对值本来就会浮动，只有「比自己上次差」才该拦。

## 4. 反馈闭环

```java
feedbackService.submit(runId, sessionId, subjectId, "UP"|"DOWN", tags, comment);
// runId 可传 null：按 session 倒查最近一条 run（前端只知道"刚才那句话"）
```

- `rating` 只接受 `UP` / `DOWN`，其他值按 `DOWN` 处理；
- `tags` 限定六类：`答非所问` `数据不对` `太慢` `编造` `太啰嗦` `其他`——自由文本会让聚类失效；
- `comment` 截断 200 字；
- 同一 run 同一调用方只保留一条（唯一键 `uk_run_subject`），重复提交按最后一次算。

`FeedbackService` 找不到可反馈的 run 时返回 `null`，前端据此隐藏「点踩」入口，而不是点了报错。

反馈与黄金集是**两个方向**：反馈发现「线上不知道的新问题」，黄金集防止「已知问题复发」。
线上点踩集中的用例，应该被手动补进 `ai_golden_case`。

## 5. 建议的关注指标

| 指标 | 健康值 | 含义 |
|---|---|---|
| `ai_hallucinated_success_total` | **恒为 0** | 有就是事故 |
| `ai_parse_fail_total / ai_run_total` | < 5% | 协议稳定性 |
| `ai_empty_result_total` | 稳定 | 突然飙高多为筛选条件或数据问题 |
| `ai_eval_score_total{label="FAIL"}` | 抽样的失败率 | 抽样评审通过率 |
| `ai_feedback_total{rating="DOWN"}` 占比 | < 5% | 用户主观感受 |
| 黄金集通过率 | 不下降 | 回归闸门 |
