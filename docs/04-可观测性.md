# 04 · 可观测性

回答三个问题，各用一套机制：

| 问题 | 机制 | 延迟 | 存在哪 |
|---|---|---|---|
| 「刚才那句为什么答错了？」 | 明细（一次 run 一行 + 每次模型/工具调用一行） | 秒级 | MySQL `ai_run` / `ai_llm_call` / `ai_tool_call` |
| 「整体在变好还是变坏？」 | 指标（25 个 `ai_*`） | 实时 | Micrometer → Prometheus |
| 「这一轮的链路长什么样？」 | 链路（span 树） | 实时 | OTel → Langfuse |

三者互不替代：明细能复盘单次事故但查不动趋势；指标能看趋势但答不了「为什么」；
链路能看到瀑布图但不适合做长期统计。

## 1. 一次 run 的生命周期

```java
// 入口处开一个 run = 一条 trace
RunScope scope = RunScope.begin(agentName, "WEB", userInput, previewChars);
try {
    AgentResult result = chatEngine.handle(...);
    scope.setOutput(result.reply());     // 幻觉规则要拿它和工具结果对账
} finally {
    obsWriter.finish(scope, status, errorCode);   // 出队，异步落库
    RunScope.clear();
}
```

`RunScope` 收集本轮的全部模型调用与工具调用（`scope.getLlmCalls()` / `getToolCalls()`），
`finish` 时打包成一个 `Batch` 投进 `ObsWriter` 的队列。

`RunScope.begin` 会自动从 `RunContext` 取 `subject_id` 与 `labels`，调用方不用传。

### 异步落库

```
业务线程 ──offer(Batch)──> ArrayBlockingQueue ──单线程──> 批量写 MySQL（每批 ≤ batch-size）
                                   │
                                   └─ 队列满 → 丢弃 + ai_obs_queue_dropped_total++
```

队列满时**丢观测、不阻塞业务**：观测是「看」的能力，不是「跑」的前提。
写失败只加 `ai_obs_write_failed_total{table=...}`，不影响对话。

`ObsWriter` 是 `AutoCloseable`，关闭时会把队列排空再退出——优雅停机不丢最后一批。

## 2. 指标（25 个）

全部以 `ai_` 开头，标签基数受控：**绝不放 userId / sessionId / traceId**（一个用户一个标签，
Prometheus 时序数会爆炸）。工具名与 model 名都是有限集合，可以放。

### 运行维度

| 指标 | 类型 | 标签 | 用途 |
|---|---|---|---|
| `ai_run_total` | Counter | `agent` `status` | 请求量、成功率 |
| `ai_run_duration` | Timer | `agent` `status` | 端到端耗时 |
| `ai_run_ttft` | Timer | `agent` | 首字延迟（体验指标） |
| `ai_run_steps` | Summary | `agent` | 步数分布，看是否绕圈 |
| `ai_run_cost_cny_total` | Counter | `agent` | 成本（元） |
| `ai_empty_result_total` | Counter | `agent` | 工具 0 条 |
| `ai_parse_fail_total` | Counter | `agent` | 模型不守 JSON 协议 |
| `ai_hallucinated_success_total` | Counter | `agent` | 工具失败但声称成功（红线） |

### 模型维度

> 所有模型指标都带 `provider` 标签，所以**按业务分渠道之后不需要加新指标**：同一个
> `ai_llm_cost_cny_total` 按 `provider` 分组就是「每条业务线各自花了多少」。
> 前提是上报的必须是**实际渠道**而不是全局默认——两套引擎都从路由解析结果里取 provider 名，
> 这一点有单测钉住。

| 指标 | 类型 | 标签 |
|---|---|---|
| `ai_llm_call_total` | Counter | `provider` `model` `status` |
| `ai_llm_duration` / `ai_llm_ttft` | Timer | `provider` `model` |
| `ai_llm_cost_cny_total` | Counter | `provider` `model` |
| `ai_tokens_total` | Counter | `provider`/`model` `kind=input|output` |
| `ai_cache_hit_tokens_total` | Counter | `provider`（前缀缓存命中，省钱指标） |
| `ai_fallback_total` | Counter | `provider`（主渠道失败切备用） |

### 工具维度

| 指标 | 类型 | 标签 |
|---|---|---|
| `ai_tool_call_total` | Counter | `tool` `status` |
| `ai_tool_duration` | Timer | `tool` |
| `ai_tool_zero_rows_total` | Counter | `tool`（查询 0 条，与 `empty_result` 互补） |

### 质量与治理

| 指标 | 类型 | 标签 |
|---|---|---|
| `ai_eval_score_total` | Counter | `metric` `label` |
| `ai_eval_judge_skipped_total` | Counter | `reason`（评审跳过原因） |
| `ai_feedback_total` | Counter | `rating` |
| `ai_golden_case_total` | Counter | `layer` `label` |

### 自身健康

| 指标 | 类型 | 说明 |
|---|---|---|
| `ai_obs_queue_depth` | Gauge | 队列积压；查不到它说明 writer 没起来，对应告警会静默失效 |
| `ai_obs_queue_dropped_total` | Counter | 丢了多少观测 |
| `ai_obs_write_failed_total` | Counter | 按表统计写失败 |

> 队列深度这个 Gauge 有个坑：`ObsWriter#start()` 里才注册。如果 writer 因为配置没启动，
> Prometheus 查不到 `ai_obs_queue_depth`，而「队列积压」的告警因此永远不会触发——
> 告警缺失比指标缺失更危险。部署后用 `curl :8080/actuator/prometheus | grep ai_obs_queue_depth`
> 自查一次。

## 3. 链路（OTel → Langfuse）

span 结构：

```
agent.run                     （一次任务，trace 名可配）
├── llm.chat                  （每次模型调用，observation.type=generation）
├── tool.order_query          （每次工具调用）
└── llm.chat
```

属性命名**必须带 `langfuse.` 前缀**：Langfuse 只认带前缀的属性，标准 OTel 属性会被塞进
`metadata.attributes` 兜底区，等于白打。

| 属性 | 说明 |
|---|---|
| `langfuse.user.id` | 调用方标识（脚手架原样透传，不解析） |
| `langfuse.session.id` | 会话 id，用于在 Langfuse 里按会话串起来 |
| `langfuse.trace.name` | trace 名称 |
| `langfuse.observation.type` | `generation` / `span` / `event` |
| `langfuse.observation.input` / `.output` | prompt 与 completion 主字段 |
| `gen_ai.system` / `gen_ai.request.model` | 厂商与模型 |
| `gen_ai.usage.input_tokens` / `.output_tokens` / `.cost` | 用量与成本 |
| `tool.name` / `tool.result_rows` / `tool.status` | 工具语义 |

**隐私开关**：`agent-kit.obs.trace-io-enabled=false` 时不把原文写进 Langfuse 的 Input/Output
（只留长度与摘要）。原文可能含用户隐私数据，这是数据留存策略的**唯一闸门**，生产环境按合规要求设。

没有配 OTel endpoint 时 `AiTracing` 退化为空实现，MySQL 明细照常写——`traceId` 会自己生成，
不会因为没接 Langfuse 就丢关联。

### 3.1 接入 Langfuse 的完整步骤

脚手架**只依赖 `opentelemetry-api`**（打 span），SDK 与导出器由使用方声明——
这是刻意的：不绑定后端，Langfuse / Tempo / 控制台都能接。接入只动使用方模块，框架一行不改。

**第 1 步：可执行应用加依赖**（参考 `examples/agent-kit-example/pom.xml`）：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-tracing-bridge-otel</artifactId>
</dependency>
<dependency>
    <groupId>io.opentelemetry</groupId>
    <artifactId>opentelemetry-exporter-otlp</artifactId>
</dependency>
```

版本全部由 Spring Boot BOM 管理，不要自己写版本号。容器里出现这三个 jar 后，
Boot 自动装配 `OpenTelemetry` Bean，`AiTracing` 的 `ObjectProvider<OpenTelemetry>`
拿到它，自动从 noop 切换到真实导出（启动日志 `ObsHub#init` 里 `tracing=otel` 即成功）。

**第 2 步：配置 OTLP 导出**（`application.yml`）：

```yaml
management:
  otlp:
    tracing:
      export:
        enabled: ${TRACE_ENABLED:false}          # 默认关，密钥就位后再开
      endpoint: ${LANGFUSE_OTLP_ENDPOINT:}       # {langfuse地址}/api/public/otel/v1/traces
      headers:
        Authorization: ${LANGFUSE_AUTH_HEADER:}  # base64(pk-lf-...:sk-lf-...)
        x-langfuse-ingestion-version: "4"
  tracing:
    sampling:
      probability: ${TRACE_SAMPLE:1.0}           # 生产建议 0.1
```

三个容易踩的坑（都是真实踩过的）：

1. **`Authorization` 必须是 base64 的 `pk-lf-...:sk-lf-...`**，生成：
   `echo -n "pk-lf-xxx:sk-lf-xxx" | base64`。密钥走环境变量 / Secret，**不进 git**（硬性约束）。
2. **`x-langfuse-ingestion-version: "4"` 不能省**：不带这个头，Langfuse 延迟最多 10 分钟入库，
   表现为「明明在打 span，面板上就是没有」。
3. **开关与密钥要么都给、要么都不给**：`export.enabled=true` 而 `Authorization` 为空时，
   每条 trace 都白跑一次 401。默认全关，验证就位后一起打开。

**第 3 步：验证**：

```bash
# 启动日志确认 tracing 已启用（noop 表示没生效）
grep "ObsHub#init" 日志    # 应看到 tracing=otel

# curl 一轮对话，然后在 Langfuse 面板按 trace 名搜 agent.run，
# 点开瀑布图应看到 llm.chat（generation）/ tool.xxx 两级子 span，
# 且 langfuse.session.id 有值、Input/Output 非空
```

**排查速查**（trace 有 trace_id 但 Langfuse 搜不到）：

| 现象 | 原因 | 处理 |
|---|---|---|
| 一条都没有 | exporter 没建 / 401 | 查 `TRACE_ENABLED` 与 `LANGFUSE_AUTH_HEADER` 是否同时给 |
| 延迟 10 分钟才出现 | 缺 ingestion 头 | 补 `x-langfuse-ingestion-version: "4"` |
| 部分缺失 | 采样率 < 1.0 | 正常代价，`ai_run.trace_id` 仍在，可用于日志关联 |
| endpoint 不可达 | 网络隔离 | 容器内 `wget -qO- {langfuse地址}` 验证 |

Langfuse 服务端自托管（v3 六容器：Postgres / ClickHouse / Redis / S3 兼容存储 / worker / web）
不在本仓库范围内；需要现成的 compose 可参考 family 项目 `deploy/` 下的实践。

## 4. 成本核算

价格来自 `ai_price` 表（唯一来源，不写在代码里）。`CostCalculator` 启动时加载并按
`price-refresh-seconds` 定期刷新。

`ai_run.cost_cny` 是本轮所有模型调用成本之和，`ai_llm_cost_cny_total` 按渠道/模型累计。
价目表为空时成本记 0 并告警——**不要**用「0 成本」当「真免费」。

## 5. 观测表

| 表 | 一行 = | 关键列 |
|---|---|---|
| `ai_run` | 一次任务 | `trace_id` `subject_id` `labels` `session_id` `agent_name` `input_hash` `input_preview` `output_preview` `status` `error_code` `step_count` `llm_call_count` `tool_call_count` `input_tokens` `output_tokens` `cached_tokens` `reasoning_tokens` `cost_cny` `ttft_ms` `duration_ms` `fallback_used` `parse_fail` `fallback_reply` `need_clarify` `empty_result` `task_success` `quality_label` |
| `ai_llm_call` | 一次模型调用 | 渠道、模型、耗时、token、成本、状态 |
| `ai_tool_call` | 一次工具调用 | 工具名、参数、结果行数、耗时、状态 |
| `ai_eval_score` | 一次评分 | 指标名、标签、理由 |
| `ai_price` | 一条价目 | 渠道、模型、输入/输出单价 |

`labels` 是 `RunContext.Subject.labels` 的 JSON（如 `{"channel":"web","role":"owner"}`），
用于业务侧自行分组。**不要往 labels 里放手机号、身份证**——它会进数据库与 trace。

保留策略：`agent-kit.obs.detail-retention-days`（默认 90）只提示不自动删，
清理任务由业务侧调度（或配 XXL-Job / crontab）执行。

## 6. 建议的看板与告警

看板（按上表可直接搭）：

1. **总览**：QPS、成功率、P95 耗时、TTFT、成本/小时
2. **质量**：`hallucinated_success` > 0 必须为 0；`parse_fail` 率；`empty_result` 率；`feedback` 正负比
3. **工具**：各工具调用量、失败率、`zero_rows` 率（突然飙高通常是筛选条件写错）
4. **模型**：分渠道耗时与成本、`cache_hit_tokens` 占比、`fallback` 率

告警（阈值按业务定，以下只是起点）：

| 告警 | 条件 |
|---|---|
| 幻觉成功 | `rate(ai_hallucinated_success_total[10m]) > 0` |
| 协议失败 | `rate(ai_parse_fail_total[10m]) / rate(ai_run_total[10m]) > 5%` |
| 观测积压 | `ai_obs_queue_depth > 1000` 持续 5 分钟 |
| 观测丢失 | `rate(ai_obs_queue_dropped_total[10m]) > 0` |
| 主渠道异常 | `rate(ai_fallback_total[10m]) > 10%` |

## 7. 开关

```yaml
agent-kit:
  obs:
    enabled: true                 # 关掉后所有埋点变 NOOP，对话不受影响
    queue-capacity: 10000
    batch-size: 50
    flush-interval-ms: 200
    preview-chars: 200            # input/output 预览截断
    args-chars: 1024              # 工具入参截断
    trace-io-enabled: true        # 是否把原文写进 Langfuse
    trace-io-chars: 8000
    detail-retention-days: 90
    price-refresh-seconds: 300
    persist-llm-call: true        # 关掉只留 ai_run，省空间
    persist-tool-call: true

# 链路导出（OTel → Langfuse），完整步骤见上文 3.1 节
management:
  otlp:
    tracing:
      export:
        enabled: ${TRACE_ENABLED:false}
      endpoint: ${LANGFUSE_OTLP_ENDPOINT:}
      headers:
        Authorization: ${LANGFUSE_AUTH_HEADER:}   # 密钥走环境变量，不进 git
        x-langfuse-ingestion-version: "4"
  tracing:
    sampling:
      probability: ${TRACE_SAMPLE:1.0}
```
