# 08 · 引擎选型（自研 / AgentScope）

脚手架里有两套对话引擎，都能独立跑完整链路，**共用一个契约、一份观测、一份评测**：

| 引擎 | 实现 | 引入方式 |
|---|---|---|
| `legacy`（默认） | `MainAgent` → `IntentRouter` → `SubAgentRunner`，自己写 ReAct 循环 | 随 `agent-kit-core` 自带，零额外依赖 |
| `agentscope` | `AgentScopeEngine` → `ReActAgent`，用框架跑 ReAct 循环 | 额外引 `agent-kit-agentscope` |

选哪套是**两件事的组合**：配置项 `agent-kit.engine` + 依赖坐标。两者必须同时对上，
否则启动失败（失败信息会直接把缺的依赖片段贴出来，见 §3）。

---

## 1. 为什么做成可选，而不是二选一写死

- **依赖代价不一样**：`agentscope` 会往 classpath 上加框架自身的依赖树。只用得到
  「多子 Agent + 工具 + 观测」的项目没理由为此付代价，所以它独立成模块，
  `agent-kit-core` 对 AgentScope **零依赖**（`mvn dependency:tree` 可验证）。
- **迁移代价不一样**：存量业务已经在 `legacy` 上跑出基线（黄金集、看板、告警阈值）。
  换引擎必须能「改一行配置回滚」，不能靠回滚代码版本。
- **行为不一样**：两套引擎在提示词装配、多轮推进、空口回执上策略不同（§4）。
  把选择权交给部署方，比在代码里替所有人拍板更合理。

## 2. 三种依赖组合

| 你需要的 | pom 里加 | 说明 |
|---|---|---|
| 最小可用 | `agent-kit-starter` | 自带 `legacy` 引擎、观测、评测、工具与 Agent 骨架。**不需要** MySQL 也能起（只是没有明细落库与会话持久化） |
| 加长期记忆与会话 | `agent-kit-starter` + `agent-kit-memory` | memory 在 starter 里已是 `optional`，不引不会报错；引了才有会话表、Redis 缓存、Milvus 记忆 |
| 换 AgentScope 引擎 | 上面 + `agent-kit-agentscope` + 配置 `agent-kit.engine=agentscope` | 两个条件缺一不可 |

```xml
<!-- 想要 AgentScope 就加这一段；不加也能用，默认走 legacy -->
<dependency>
    <groupId>com.beastmouth.kit</groupId>
    <artifactId>agent-kit-agentscope</artifactId>
    <version>${agent-kit.version}</version>
</dependency>
```

## 3. 配置与启动期校验

```yaml
agent-kit:
  # legacy（默认，可省略）| agentscope
  engine: legacy
```

- **不写这一行 = `legacy`**（`matchIfMissing = true`），存量应用不需要改配置。
- 只认 `legacy` / `agentscope` 两个词（常量在 `ChatEngine.LEGACY` / `ChatEngine.AGENTSCOPE`）。
  匹配**忽略大小写**——这是 Boot `@ConditionalOnProperty` 的行为，`agentScope` 能正常生效；
  但写成 `agent_scope` / `agent-scope` 就一定失败。
- `agent-kit.agentscope.*` 只在 `engine=agentscope` 时绑定生效，配了也不会污染 legacy。

四种组合里两种是对的，两种会在启动期被拦下（**在 `Started` 之前**，不会带着错配置对外服务）。
拦下它们的是 `EngineGuard`（校验 + 日志）和 `missingChatEngine`（兜底 Bean，负责产出人话报错）：

| 配置 | classpath 有 agentscope 模块 | 结果 |
|---|---|---|
| 不配 / `legacy` | 否 | ✅ 自研引擎 |
| 不配 / `legacy` | 是 | ✅ 自研引擎 + 一条 INFO：模块在但没启用（常见于「加了依赖忘改配置」） |
| `agentscope` | 是 | ✅ AgentScope 引擎 |
| `agentscope` | 否 | ❌ 报错，正文直接给出要加的 `<dependency>` 坐标 |
| `agent_scope`（拼成别的词） | 任意 | ❌ 报错，列出合法值 |

> **为什么要专门写这两件东西**：只写 Guard 是不够的。业务代码里只要有一处直接注入
> `ChatEngine`（几乎所有接入方都会这么写），容器在创建那个 Bean 时就失败了，
> `EngineGuard#afterSingletonsInstantiated` 根本轮不到执行，报错仍然是
> 「required a bean of type ChatEngine that could not be found」——看不出根因在依赖坐标还是配置值。
> 所以真正的载体是 `@ConditionalOnMissingBean` 的 `missingChatEngine`：容器拿到一个
> 「创建即抛异常」的实现，异常正文就是下面这段话，且只在**一个引擎都没注册**时出现。
>
> ```
> 配置 agent-kit.engine=agent_scope 没有匹配到任何 ChatEngine 实现。
> 合法值只有 legacy（默认，随 agent-kit-core 自带）与 agentscope（需额外引模块；匹配忽略大小写）。
>
> 用 AgentScope 需要同时做两件事，缺一不可：
>   1) 业务 pom 里加依赖：
>      <dependency>
>          <groupId>com.beastmouth.kit</groupId>
>          <artifactId>agent-kit-agentscope</artifactId>
>          <version>${agent-kit.version}</version>
>      </dependency>
>   2) 配置 agent-kit.engine=agentscope
>
> 若只是想用默认引擎，把这一行改成 legacy（或直接删掉）。
> 判据与完整说明见 docs/08-引擎选型.md。
> ```
>
> 两处共用 `EngineGuard#noEngineMessage` 一份文案，`EngineGuardTest` 的 5 个用例钉住它，
> 改文案时不会悄悄退化。

## 4. 两套引擎的差异

| 维度 | `legacy` | `agentscope` |
|---|---|---|
| ReAct 循环 | `SubAgentRunner` 自己写：模型输出 JSON（`{"tools":[...]}` / `{"reply":"..."}`），循环到出 `reply` 或撞 `max-steps` | 框架 `ReActAgent` 驱动，`maxIters = agent-kit.max-steps` |
| 提示词装配 | `PromptFragments` + `prompt-order=v1/v2`（v2 把易变内容压到尾部提缓存命中） | `PromptTailMiddleware#onSystemPrompt` 统一在尾部追加日期、记忆、无思考提示 |
| 工具接入 | 直接 `AgentTool#execute`，白名单由 `Agent#toolNames` 控制 | `ToolBridge` 把同一个 `AgentTool` 包成框架工具，**拦截器、白名单、`rows` 语义完全一致** |
| 模型容错 | `FailoverModelProvider`（主备 + 冷却期） | `ResilientModel`（同一套主备策略，接框架的 Model 接口） |
| 空口回执 | 由质量规则 R4 事后判定 | `write-claim-guard` 当场补一轮强制纠正（`agent-kit.agentscope.write-claim-guard`） |
| 前端状态文案 | 固定措辞 | `agent-kit.agentscope.tool-labels` 按工具名映射 |
| 观测 | `RunScope` + `ToolCallRecorder` + `LlmCallRecorder` | `ObservingHook` + `RuntimeObs`，写**同一批** `ai_*` 表与指标 |
| 黄金集 | `batchId` 带 `GLEGACY-...` | `batchId` 带 `GAGENTSCOPE-...`，两批可对比 |

**共享的部分**（换引擎不用动）：`Agent` / `AgentTool` / `ToolRegistry` / `ToolInterceptor` /
`RunContext` / `TurnHook` / `IntentRouter` / `AgentRegistry` / 全部 `ai_*` 表 / 质量规则与黄金集 /
会话与记忆模块。所以**换引擎不需要改业务代码，也不需要改看板**。

## 5. 什么时候选哪个

**先看产品形态，再看技术偏好。** 顺序反了就会得出「框架功能更多所以选框架」这种结论——
而框架功能多，恰恰是业务对话型产品不需要的那部分。

### 5.1 按产品形态分

| 产品形态 | 典型需求 | 建议 |
|---|---|---|
| **业务对话型**（客服、记账、工单、查询、办理、审批） | 多轮短会话 + 强工具调用 + 可审计 + 成本可控 | **legacy 或 agentscope 均可；不要上 `HarnessAgent`** |
| **长程任务型**（调研、运维处置、数据分析流水线） | 多步推进 + 状态恢复 + 中间产物落文件 | `agentscope` + `HarnessAgent` |
| **代码/环境操作型**（coding agent、自动化脚本、批处理） | 沙箱执行 + 文件读写 + 命令隔离 | `HarnessAgent`，**不要自研沙箱** |

判据一句话：**Agent 是「替人查和办」，还是「替人做」？**
「查和办」是对话型，账本和工具是核心；「做」是任务型，执行环境是核心。

### 5.2 三个倒向信号

出现**任意两个**，就该认真考虑迁 `HarnessAgent`（只让它管推理与执行层，业务账本仍留在本仓库）：

1. **有人提「让 Agent 自己跑代码 / 改文件」** —— 沙箱隔离是安全工程，不是业务代码，自研等于给自己埋事故；
2. **单会话 30 轮成为常态** —— `historyLimit=12` 从第 13 轮开始就在丢信息，需要压缩而不是截断（见 [10-上下文压缩接入](10-上下文压缩接入.md)）；
3. **需要跨会话、跨天的任务连续性** —— 今天的任务明天接着做，靠 MySQL 会话表拼不出来，需要 `AgentState` 这类显式任务状态。

**这三条与「业务对话」几乎不重叠。** 业务对话的典型形态是「短会话、强工具、要能查账」，
三个信号一个都不占——这不是巧合，是两种产品的工作方式不同。

### 5.3 业务对话型为什么本仓库的形态更合适

| 维度 | 本仓库 | `HarnessAgent` |
|---|---|---|
| 会话 | MySQL 实体：列表、分页、改名、渠道只读、上限，都是产品功能 | `AgentState` 快照，按 `(userId,sessionId)` 寻址，无列表/改名语义 |
| 租户 | `namespace` + `owner` + `sessionId` 三层，归属校验在 SQL 收口 | `(userId, sessionId)` 两层，靠 key 前缀 |
| 成本 | 前缀缓存可调（`prompt-order=v2`），`ai_llm_call` 逐条可算 | 默认 compaction 每次重写前缀，**会打掉前缀缓存** |
| 审计 | `ai_run` / `ai_llm_call` / `ai_tool_call` 全在 SQL，能导能对账 | OTel 链路追踪，没有业务成本语义 |
| 质量 | R1–R9 + LLM 评审 + 黄金集 + 反馈闭环 | 无对应能力 |
| 故障 | 出问题打开 IDE 改 | 框架内部问题只能提 issue 等修 |

**一句话**：业务对话型产品，真正难的是「账算得清、话不出错、出事能查」，这三件事框架帮不上忙，
反而会多一层不可控。这类产品该把力气花在工具质量、提示词、评测上，而不是换推理框架。

### 5.4 技术偏好层面的取舍

**选 `legacy`**：
- 只想要「多子 Agent + 工具 + 观测」，不想多背一层框架依赖；
- 已有基线在 legacy 上，短期没有换的动力；
- 需要完全掌控提示词拼装顺序（例如已经在做前缀缓存优化）。

**选 `agentscope`**：
- 需要框架侧的 ReAct 循环与中间件栈，不想自己维护 `SubAgentRunner`；
- 未来可能逐步接沙箱 / Plan Mode / 声明式 subagent，先把 `ChatEngine` 的位置占住；
- 接受多一层依赖，换取循环实现的维护成本下降。

两套都不满意时：实现 `ChatEngine`（3 个方法），自己注册成一个 Bean，
把 `agent-kit.engine` 设成它的 `engineName()`——`EngineGuard` 会校验配置与实现是否一致。

## 6. 切换与回滚

**切换**（一次重启）：

```bash
# 1) 依赖：加 agent-kit-agentscope
# 2) 配置：agent-kit.engine=agentscope（或环境变量 AGENT_KIT_ENGINE=agentscope）
# 3) 重启后确认日志
#    AgentScopeConfig#init#Agent 引擎切换为 agentscope
#    EngineGuard#check#Agent 引擎 = agentscope（AgentScopeEngine），AgentScope 模块在 classpath 上
```

**回滚**：把配置改回 `legacy` 重启即可，不需要回滚代码版本（依赖留着无害，
只会多打一条「模块在但没启用」的 INFO）。

**刻意不做运行期热切换**：两套引擎的 `ReActAgent` 构建、提示词缓存、观测 RunScope
都是按轮创建/线程绑定的，热切会让同一会话的前后两轮跑在不同引擎上，
黄金集与看板数据立刻失去可比性。要灰度就**按实例灰度**——一批实例切配置，
用同一份黄金集各跑一遍，比 `batchId` 里的引擎名。

## 7. 排查对照表

| 现象 | 原因 | 处理 |
|---|---|---|
| 启动报「没有 ChatEngine」且正文含 `<dependency>` | `engine=agentscope` 但没引模块 | 加 `agent-kit-agentscope` |
| 启动报「没有 ChatEngine」且正文列了合法值 | `engine` 写成了别的词（如 `agent_scope`） | 改成 `legacy` / `agentscope` |
| 堆栈里出现 `missingChatEngine` | 这是兜底 Bean 在报错，说明一个引擎都没注册 | 看它给出的正文，按提示补依赖或改配置 |
| 启动报「生效的引擎是 X，配置是 Y」 | 有人手动注册了 `ChatEngine` Bean | 去掉自定义 Bean，或把配置改成 X |
| 日志有「模块在 classpath 上但 legacy 生效中」 | 加了依赖没改配置 | 改 `agent-kit.engine` |
| 切到 agentscope 后工具行为变了 | 不该发生——两个引擎共用 `ToolInterceptor` 与白名单 | 先查 `agent-kit.agentscope.tool-labels` 是否只是文案差异；行为差异请提 issue |
| 切引擎后黄金集分数掉 | 两套引擎基线不同，不能直接比 | 用同引擎自身的上一批基线比；`batchId` 区分 |
| 上游断流后正文**重复两三遍** | AgentScope 框架自带模型级重试（`ModelUtils` 的 `retryWhen`，默认 `maxAttempts=3`），重试是重订阅整条流，已推送的增量会重新推一遍 | 见下方「已知限制」；要杜绝重复就选 legacy，或在网关层重试 |

### 7.1 已知限制：AgentScope 的模型级重试会重放已输出正文

流式一旦开始，HTTP 200 与响应头已经发出去了。AgentScope 的模型调用在 `ChatModel` 内部
按 `GenerateOptions.executionConfig` 重试（默认 3 次），而重试是**重新订阅整条流**，
不是断点续传——前两次吐出去的字会再吐一遍。

实测结论（2026-11-17，本机断流冒烟）：

- 现象：同一段正文重复 3 遍，末尾跟一个 `error` 帧，HTTP 200，`ai_run.status=FAIL`。
- `ReActAgent.Builder#modelExecutionConfig(...)` **改不动它**：那条配置进不了模型调用最终的
  `GenerateOptions`，写 `maxAttempts(1)` 也不影响重试次数。别在这里浪费时间。
- 脚手架已做的两件事：`ResilientModel` 拒绝「上层对同一条流重订阅」的重放；`ChatModel` 内部
  这一层拦不住。

需要「不重复」时的三个选择：用 legacy 引擎（自研循环没有模型级重试，失败即 `error` 帧收尾）、
把重试放到网关（Kong/Nginx/服务网格），或接受重复——它至少不会丢内容，也不会让连接悬着。
