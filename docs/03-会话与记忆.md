# 03 · 会话与记忆

两个容易混的东西，这里先切开：

| | 会话（session） | 记忆（memory） |
|---|---|---|
| 时间尺度 | 一次对话内，几轮到几十轮 | 跨会话，长期 |
| 存什么 | 用户与助手的原话、哪个 Agent 答的、工具动作 | 提炼出来的稳定信息（偏好、事实、习惯、规则） |
| 怎么取 | 按会话 id 查最近 N 条，顺序拼接 | 按语义相似度检索，与当前问题相关才注入 |
| 容量 | 有界（`history-limit`） | 有界（`max-per-owner`，超出淘汰最旧） |
| 存储 | MySQL 正文 + Redis 上下文包 | MySQL 正文 + Milvus 向量 |

会话保证「这轮能接着上轮说」；记忆保证「上周说过的事这周还记得」。

---

## 1. 隔离原语：namespace + owner

所有会话与记忆访问都带这两个参数，**没有任何方法从 `RunContext` 偷偷读**。

```java
sessionStore.recentHistory(sessionId, namespace, owner);
memoryService.recall(namespace, owner, message);
```

为什么不隐式读上下文：忘设上下文时，显式参数会编译不过或传 null 报错；
隐式读取只会静默读到空数据——答得不对，但一切正常。

| 参数 | 含义 | 谁决定 |
|---|---|---|
| `namespace` | 分区键：租户 / 组织 / 项目 / 机器人实例 | 服务端配置或登录态，**绝不让客户端传** |
| `owner` | 归属方：用户 id / 工单号 / 设备号 | 鉴权结果 |
| `owner = null` | 该分区内**共享**（任何 owner 检索都会带上共享记忆） | 共享语义不单独建字段，少一个状态少一处不一致 |

`AgentSessionStore` 的归属校验在这里收口：别人的会话一律按「不存在」处理，
不区分「没有」与「无权访问」，避免通过 ID 探测他人会话。

## 2. 会话

### 2.1 生命周期

```java
// 新建（第 4 个参数是渠道，第 5 个是渠道内来源标识，网页一般传 owner）
AgentSession session = sessionStore.create(namespace, owner, "新对话",
        AgentSession.CHANNEL_WEB, owner);

// 读：getRequired 不存在就抛；getWritable 额外校验可写（只读会话不能追加）
sessionStore.getRequired(sessionId, namespace, owner);
sessionStore.getWritable(sessionId, namespace, owner);

// 列表（按最近活跃倒序）、改名、删除
sessionStore.list(namespace, owner);
sessionStore.rename(sessionId, namespace, owner, "报税材料");
sessionStore.delete(sessionId, namespace, owner);
```

### 2.2 标题自动生成

`append(..., "USER", ...)` 在**这是会话第一条消息**时把标题改成消息前 24 字。
判据是「messageCount 是否为 0」，不是比较标题字符串——前端会带本地化占位标题
（「新会话」/「New chat」），比字符串的话英文用户永远改不了标题。

### 2.3 渠道隔离

网页与 IM 各走各的会话（`channel` 字段）。IM 场景想「一直在同一个会话里聊」，
用 `latestBySource(namespace, owner, channel, sourceId)` 取渠道内最近一次活跃的会话。

`SessionSourceRegistry` 是可选扩展点：解绑后历史自动隐藏、重新绑回又自动出现，
不必删数据。没有实现时列表只按 `owner` 过滤。

### 2.4 上下文缓存（Redis）

`AgentContextCache` 缓存「历史消息 + 最后应答的 Agent」，key 为
`agent-kit:ctx:{namespace}:{owner}:{sessionId}`。

- **读**：命中直接用，miss 回源 MySQL 并回填；
- **写穿**：`append` 在事务内追加并回写缓存，且做**乐观校验**——
  只有缓存里的 `lastMessageId` 与追加前库中最新 ID 一致才写，否则 evict。
- **降级**：Redis 任何异常都当 miss，关掉开关即回退纯 MySQL。

缓存永远是优化，不是正确性前提。用脏包覆盖新数据比多查一次库严重得多。

### 2.5 会话锁

同一个会话的两个并发请求会各读一份历史、各自追加，最后库里出现两条互不知情的回答。
`AgentSessionLock.tryRun(sessionId, waitMillis, action)` 把整轮串行化：

| 场景 | 等待时长 | 理由 |
|---|---|---|
| 网页 | `WEB_WAIT_MILLIS = 0` | 用户能自己重发，等锁只会让请求堆着 |
| IM | `IM_WAIT_MILLIS = 5000` | 用户发完就等回复，短等一下比报错体验好 |

拿到锁才执行，拿不到返回 `false`，由调用方提示「正在处理上一条消息」。

## 3. 记忆

### 3.1 四类 + 两态

| `kind` | 内容 | 例子 |
|---|---|---|
| `PREFERENCE` | 偏好 | 「回答用表格，不要长段落」 |
| `FACT` | 稳定事实 | 「负责华东区，汇报对象是张三」 |
| `HABIT` | 表达习惯 | 「说『这单』指最近一次提到的订单」 |
| `RULE` | 业务规则 | 「金额单位一律用万元」 |

| `status` | 含义 |
|---|---|
| `ACTIVE` | 生效中，检索与提炼都只看这个 |
| `SUPERSEDED` | 被新记忆取代。UPDATE/DROP 不物理删，保留「以前是什么口径」的痕迹 |

`RULE` 在检索时占**独立槽位**（`rule-top-k`，默认 3）且排在前面，防止规则越攒越多后
把普通记忆全挤出结果；规则不足时名额让渡，总条数仍 ≤ `top-k`。

### 3.2 检索（读路径，同步）

```java
List<String> memories = memoryService.recall(namespace, owner, message);
// 返回形如 "[PREFERENCE] 回答用表格…" 的行文本，直接进系统提示词
```

内部顺序：嵌入（`bge-m3` 等 OpenAI 兼容 `/v1/embeddings`）→ `ensureReady()` 校验 Milvus 结构
→ 个人记忆与共享记忆**各搜一遍**（都带 namespace 过滤）→ 按相似度归并 → 回 MySQL 取正文
并按 kind 分槽 → 低于 `min-score` 丢弃。

任何一步失败返回空列表，不影响本轮对话。

> 结构校验必须在检索之前：结构重建后索引是空的，不立刻按 MySQL 灌回，检索会一直返回空，
> 表现是「记忆全丢了」但没有任何报错。`ensureReady()` 会置 `takeLegacyResetSignal()`，
> 上层据此触发 `rebuildFromMysql()`。

### 3.3 提炼（写路径，异步）

```java
memoryService.consolidateAsync(namespace, owner, sessionId, userMessage, assistantReply);
```

- 单线程执行器（多线程反而可能乱序写）；
- 同一 owner 同一时刻只允许一次（`agent-kit:lock:memory:{namespace}:{owner}`），
  拿不到就跳过，下一轮再试，不排队；
- 由模型判断「这一轮有没有值得记的」，输出 ADD / UPDATE / DROP 指令；
- 提示词模板可用 `agent-kit.memory.consolidate-prompt` 整体替换（业务口径不该写死在脚手架里）。

**为什么异步**：提炼要再调一次模型，慢且可失败。放同步路径上等于让用户多等几秒，
换一个「下次可能记得」的能力。

### 3.4 手动维护

```java
memoryService.addSharedMemory(namespace, AgentMemory.KIND_RULE, "金额单位一律用万元");
memoryService.mergeRules(namespace, owner, List.of(dropId1, dropId2), "合并后的规则");
memoryService.rebuildFromMysql();      // 索引丢了/换 collection 后重建
```

## 4. 表与 key

| 对象 | 位置 | 关键列 |
|---|---|---|
| `ai_agent_session` | MySQL | `namespace` `owner` `title` `channel` `source_id` `agent_name` `message_count` `last_message_at` |
| `ai_agent_message` | MySQL | `session_id` `namespace` `owner` `role` `agent_name` `content` `tool_events` |
| `ai_agent_memory` | MySQL | `namespace` `owner`(可空) `kind` `content` `source_session_id` `status` |
| `agent-kit:ctx:*` | Redis | 上下文包（历史 + lastMessageId） |
| `agent-kit:lock:session:*` | Redis | 会话锁 |
| `agent-kit:lock:memory:*` | Redis | 提炼锁 |
| `ai_agent_memory` | Milvus | `id` `namespace` `owner`(共享写空串) `vector` |

Milvus 的标量字段不支持 null，所以共享记忆的 `owner` 写空串——这是唯一的表示差异，
查询时统一转换成 null。

## 5. 配置

```yaml
agent-kit:
  context-cache-enabled: true       # Redis 上下文缓存，关掉退回纯 MySQL
  context-cache-ttl-seconds: 1800
  max-sessions-per-owner: 50        # 超出拒绝新建（SESSION_LIMIT）
  history-limit: 12                 # 每轮取多少条历史

  memory:
    enabled: false                  # 打开需要 Milvus + 嵌入模型
    base-url: http://localhost:11434/v1
    model: bge-m3
    dimensions: 1024
    milvus-uri: http://localhost:19530
    collection: ai_agent_memory     # 生产环境务必改成自己的名字
    top-k: 5
    rule-top-k: 3
    min-score: 0.35
    max-per-owner: 200
    chat-provider: ollama           # 提炼专用渠道，留空沿用主链路
```

## 6. 三个坑

**1. 共用 Milvus 时没改 collection 名**
默认 `ai_agent_memory` 是通用名。同实例上跑两套 agent，记忆会互相串；
`rebuildFromMysql()` 还会把你的表灌进共用集合。接生产前改成 `<你的系统>_memory`。

**2. 以为 `owner = null` 是「查不到」**
`null` 是「分区内共享」，不是「无归属」。租户级规则就靠它，别过滤掉。

**3. 记忆方法隐式读上下文**
早期版本会从 `RunContext` 取 `tenantId/userId`，忘了设就静默查到空数据。现在全部显式传参——
如果你的业务封装了一层，也请保持一致，不要在外面补一个「自动从上下文取」的便利方法。
