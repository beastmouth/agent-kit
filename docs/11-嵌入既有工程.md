# 11 · 把 agent-kit 嵌进一个已有 Agent 工程（实测记录）

> **结论先行：技术上能共存，功能上零收益。**
> 本章记录 2026-11-19 把 `agent-kit-starter` 整包引入 `family`（一个已有自研 Agent 的
> Boot 3.3.5 单体）的完整实测过程，包含 4 个必踩的坑与修改点。
> 如果两套实现只是并存、不做迁移，**不要这么做**——见 §6。

---

## 1. 适用场景

| 场景 | 要不要整包引入 |
|---|---|
| 新项目，没有存量 Agent 实现 | 直接引，不用看本章 |
| 已有自研 Agent，想**逐步迁移**到 agent-kit | 看本章 §3，先把容器跑通 |
| 已有自研 Agent，只想拿某几个能力（压缩、截断、评测） | **不要整包引入**，搬到自己的包下即可，见 [10-上下文压缩接入](10-上下文压缩接入.md) |

判定信号：如果宿主工程里已经存在与 `agent-kit` 同名的组件类（`ChatEngine`、`ToolRegistry`、
`AiConfig`、`runMapper`…），整包引入就是一个「让两套实现住进同一个容器」的工程问题，
而不是「加一行依赖」的配置问题。

---

## 2. 前置差异清单（先确认，别急着加依赖）

| 项 | 宿主（实测样本） | agent-kit | 是否阻塞 |
|---|---|---|---|
| Spring Boot | 3.3.5 | 4.1.2 | 是，见 §3.1 |
| MyBatis-Plus starter | `spring-boot3-starter:3.5.7` | `spring-boot4-starter:3.5.18` | 是，见 §3.1 |
| JDK | 17 | 17 | 否 |
| 包名 | `com.beastmouth.family.*` | `com.beastmouth.agentkit.*` | 否（类不冲突，Bean 冲突） |

## 3. 四个必踩的坑

按实际遇到顺序，每个都附现象与改法。

### 3.1 Boot 4 的 MyBatis starter 在 Boot 3 下启动即崩

**现象**：

```
java.io.FileNotFoundException:
  class path resource [com/baomidou/mybatisplus/autoconfigure/ShardingAutoConfiguration.class]
  cannot be opened because it does not exist
    at AutoConfigurationSorter$AutoConfigurationClass.getAnnotationMetadata
```

**原因**：`mybatis-plus-spring-boot4-starter:3.5.18` 的 `AutoConfiguration.imports` 声明了
`ShardingAutoConfiguration`，而 Boot 3 侧实际解析到的是 `mybatis-plus 3.5.7` 的类路径，
该类在 3.5.7 里不存在。

**改法（宿主侧，一处 exclusion）**：

```xml
<dependency>
    <groupId>com.beastmouth.kit</groupId>
    <artifactId>agent-kit-starter</artifactId>
    <version>0.1.0</version>
    <exclusions>
        <exclusion>
            <groupId>com.baomidou</groupId>
            <artifactId>mybatis-plus-spring-boot4-starter</artifactId>
        </exclusion>
    </exclusions>
</dependency>
```

宿主已有 `spring-boot3-starter` 时这样最省；宿主没有 MyBatis 时才需要换成 boot3 starter。

### 3.2 同名组件 → 扫描期直接抛异常，`allow-bean-definition-overriding` 管不了

**现象**：

```
ConflictingBeanDefinitionException: Annotation-specified bean name 'aiConfig'
for bean class [com.beastmouth.agentkit.config.AiConfig] conflicts with existing,
non-compatible bean definition of same name and class [com.beastmouth.family.agent.config.AiConfig]
```

**为什么开 `spring.main.allow-bean-definition-overriding=true` 也没用**：
异常抛在 `ClassPathBeanDefinitionScanner#checkCandidate`，扫描期发现同名不同类就直接抛，
这个开关只影响注册期的覆盖行为，管不到扫描期。

**改法（agent-kit 侧，一行）**：让扫描出来的 Bean 名带全限定名。

```java
@ComponentScan(basePackages = "com.beastmouth.agentkit",
        nameGenerator = FullyQualifiedAnnotationBeanNameGenerator.class)
```

改完 `aiConfig` 变成 `com.beastmouth.agentkit.config.AiConfig`，与宿主的 `aiConfig` 共存。
副作用：任何按 Bean 名注入（`@Qualifier("aiConfig")`）或 `getBean("aiConfig")` 的代码会失效——
本仓库内没有这类写法，接入方需要自查。

### 3.3 Mapper 一个都不会注册

**现象**：

```
Parameter 0 of constructor in com.beastmouth.agentkit.obs.CostCalculator
required a bean of type 'com.beastmouth.agentkit.obs.mapper.AiPriceMapper' that could not be found.
```

**原因**：宿主的 `@SpringBootApplication` 只扫自己的包；MyBatis 的
`AutoConfiguredMapperScannerRegistrar` 也只认主类所在包。starter 里的 `@Mapper` 接口
在别人的工程里根本不在扫描范围内。示例项目能跑，是因为示例的主类恰好就在
`com.beastmouth.agentkit` 下——这是 starter 的自洽性缺陷。

**改法（agent-kit 侧）**：自动配置类上显式声明 Mapper 扫描。

```java
@MapperScan(basePackages = "com.beastmouth.agentkit",
        annotationClass = Mapper.class,
        nameGenerator = FullyQualifiedAnnotationBeanNameGenerator.class)
```

### 3.4 `@MapperScan` 不限定注解，会把业务接口代理成 Mapper

如果不写 `annotationClass = Mapper.class`，包下**所有接口**都会被 MyBatis 注册：

```
BindingException: Invalid bound statement (not found): com.beastmouth.agentkit.provider.ModelProvider.id
```

`ModelProvider` 是普通业务接口，被 Mapper 代理后调任何方法都找不到 SQL。
`annotationClass` 与 `nameGenerator` 两个属性都必须写。

## 4. 改完之后的实际状态

启动成功（4.7s，health UP），但要看清容器里发生了什么：

```
AgentRegistry#init#已注册子Agent=[]        ← 宿主自己的 Agent 不在 kit 的扫描范围
ToolRegistry#init#已注册工具=[]            ← 同上，工具一个都没接
EngineGuard#check#Agent 引擎 = legacy（MainAgent）  ← kit 自己的空引擎
ObsWriter#start#观测写入线程已启动 capacity=10000   ← 额外起了一个后台线程
```

宿主业务代码注入的是 `com.beastmouth.family.agent.agent.ChatEngine`，
kit 提供的是 `com.beastmouth.agentkit.agent.ChatEngine`——**两个不同的接口类型**，
所以类型注入不冲突，各走各的。这就是「能启动」的真正原因：不是融合了，是并排放着。

---

## 5. 表结构不兼容：一旦真跑就会报错

两套实现都映射同名表 `ai_run`，但列不同：

| | `ai_run` 关键列 |
|---|---|
| 宿主（family） | `id, trace_id, user_id, tenant_id, session_id, channel, agent_name, ...` |
| agent-kit `RunMapper` | 使用 `subject_id`，宿主表里没有这一列 |

后果：kit 的观测一旦被触发（比如把宿主的工具注册进 kit 的 ToolRegistry），
写入会 `Unknown column 'subject_id'`。**并存期没报错，只是因为 kit 那条链路没被走过。**

---

## 6. 结论：什么时候值得做

**不值得**（本次实测场景）：宿主已有完整的 Agent 实现，只是想让 kit 的能力也能用。
整包引入的净新增能力是 0——kit 的 Agent/Tool 注册表是空的，宿主也不会去用它。
多出来的成本：一个后台线程、两套 Mapper、两套 model registry，以及本节列的 4 个坑。

**值得**：真的要把宿主的 Agent/Tool 迁到 kit 上，也就是接受「删掉宿主实现」。
那时顺序应该是：

1. 先按 §3 把容器跑通（并存，宿主不受影响）；
2. 把宿主的工具逐个实现为 kit 的 `AgentTool`，注册进 kit 的 `ToolRegistry`；
3. 把宿主的子 Agent 迁到 kit 的 `Agent` 契约；
4. 统一切换 `ChatEngine` 实现，宿主旧实现下线；
5. 对齐表结构（`subject_id` vs `user_id`），或给 kit 的 Mapper 加列映射。

**只想要某个能力**（上下文压缩、工具结果截断、成本报表）：搬到宿主自己的包里，
不要引入整个 starter。参照 [10-上下文压缩接入](10-上下文压缩接入.md)，那 8 个类
加起来不到 800 行，且不依赖 kit 的其余部分。

## 7. 复现与验证

```bash
# 1. 宿主加依赖（含 §3.1 的 exclusion）
# 2. agent-kit 装到本地仓库（Boot 4 的 install 插件常缺，用 3.1.3）
mvn -o -DskipTests package
mvn -o org.apache.maven.plugins:maven-install-plugin:3.1.3:install-file \
    -Dfile=pom.xml -DpomFile=pom.xml -Dpackaging=pom      # 父 pom 必须先装
for m in agent-kit-core agent-kit-memory agent-kit-agentscope agent-kit-starter; do
  mvn -o org.apache.maven.plugins:maven-install-plugin:3.1.3:install-file \
      -Dfile=$m/target/$m-0.1.0.jar -DpomFile=$m/pom.xml
done

# 3. 宿主重打包启动（注意 clean，否则 BOOT-INF/lib 里还是旧 jar）
mvn -o -DskipTests clean package -pl <bootstrap-module>
java -jar <bootstrap-module>/target/<app>.jar --server.port=18081
```

**验证判据**：
- 启动日志出现 `Started <App>`，health = UP；
- 日志里 `AgentRegistry#已注册子Agent=[]`、`ToolRegistry#已注册工具=[]`——如果非空，
  说明宿主和 kit 的组件真的在同一批扫描里，需要逐项检查是否重复注册。
