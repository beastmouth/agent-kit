# 06 · 接入清单

给「准备把一个真实业务接进来」的人。按顺序打勾，每步都有验收方式——**没验收就等于没做**。

---

## 0. 先做四个决定

| 决定 | 选项 | 影响 |
|---|---|---|
| 要不要长期记忆 | 要 → 需要 Milvus + 嵌入模型 | 不要就先 `memory.enabled=false`，接口留好以后能开 |
| 要不要会话缓存 | 要 → 需要 Redis | 不要也能跑，只是每轮多几次 MySQL 查询 |
| 单租户还是多租户 | 单 → `namespace` 固定一个值 | 多 → 从登录态取，**绝不让客户端传** |
| 几个子 Agent | 1 个就够就别拆 | 拆分的依据是「工具集与提示词口径不同」，不是「代码好看」 |

---

## 1. 骨架（必做）

- [ ] 加 `agent-kit-starter` 依赖（要记忆再加 `agent-kit-memory`）
- [ ] 启动类加 `@MapperScan`，列出脚手架四个 mapper 包
- [ ] 执行 `db/agent-kit-schema.sql`，确认 10 张 `ai_*` 表存在
- [ ] 配 `agent-kit.provider` / `base-url` / `model` / `api-key`
- [ ] 起服务后确认日志里有 `ModelProviderRegistry#init#已注册提供方=[...]`

**验收**：能起服务，`ai_run` 表可写（随便调一次对话后 `select count(*) from ai_run`）。

---

## 2. 工具（必做）

- [ ] 为每个领域写一个 `ToolGroup`，内部类实现 `AgentTool`
- [ ] 每个工具写清 `description`：**「什么时候该用」而不是「怎么实现」**
- [ ] `parametersSchema` 是真的 JSON Schema（`required` 别漏）
- [ ] `rows` 三态填对（查询 0 条 → 0；写操作 → 影响行数；不产出行 → null）
- [ ] 失败用 `ToolOutcome.fail(msg)`，msg 写成能给用户看的话
- [ ] 工具里需要调用方标识时用 `RunContext.subjectId()`，不要加方法参数

**验收**：日志里有 `ToolRegistry#init#已注册工具=[...]`，且工具数与预期一致。

---

## 3. 子 Agent（必做）

- [ ] 每个领域一个 `@Component implements Agent`
- [ ] `description` 写清「什么请求归你」，主 Agent 只靠这句话路由
- [ ] `toolNames` 是白名单，**只放本领域工具**
- [ ] `systemPrompt` 只写业务口径，不写工具清单、不写 JSON 协议
- [ ] 含糊时怎么办、做不到时怎么答，明确写进提示词

**验收**：`AgentRegistry#init#已注册子Agent=[...]`，数量正确。

---

## 4. 身份与上下文（必做）

- [ ] 实现一个 `SubjectScope` 类似的类：`open(subject)` → `AutoCloseable`，close 里 `clear()`
- [ ] 入口处 `try (var ignored = SubjectScope.open(...)) { ... }`，或在 `finally` 里 `clear()`
- [ ] `namespace` 从服务端配置/登录态取，不从请求体取
- [ ] `owner` 从鉴权结果取，不用客户端自报

**验收**：`ai_run.subject_id` 有值且正确；两个不同调用方互相看不到对方的会话。

---

## 5. 会话与记忆（要就做）

- [ ] 会话：`create` / `getWritable` / `recentHistory` / `append` 四件套接通
- [ ] 会话读写**放在同一个锁里**（`AgentSessionLock.tryRun`）
- [ ] 调模型前 `RunScope.bindSession(sessionId)`，`finally` 里 `unbindSession()`
- [ ] 记忆：`recall` 放锁外，`consolidateAsync` 放锁外异步
- [ ] 用记忆就把 `agent-kit.memory.collection` 改成自己的名字
- [ ] 需要租户级规则时用 `addSharedMemory(namespace, KIND_RULE, ...)`（`owner` 为空即共享）

**验收**：
- 同一会话追问「还有呢」能接上上一轮；
- `POST /feedback` 能按会话倒查到 runId（倒查不到说明第 3 步漏了）；
- `ai_agent_message` 里一轮有两条（USER + ASSISTANT）。

---

## 6. 准入与钩子（按需）

- [ ] 权限/审计/限流写 `ToolInterceptor`，返回字符串即拒绝，永不抛异常
- [ ] 多个拦截器用 `@Order` 定序，数值小的先跑
- [ ] 每轮一次的准备工作写 `TurnHook`，不要塞进工具拦截器

**验收**：故意用一个无权限的调用方触发写工具，日志里有 `工具被拦截`，且模型如实转述原因、
**没有重试同一个工具**。

---

## 7. 可观测（建议做）

- [ ] `agent-kit.obs.enabled=true`（默认）
- [ ] `/actuator/prometheus` 能查到 `ai_run_total` 与 `ai_obs_queue_depth`
- [ ] 配 OTel endpoint 后 Langfuse 能看到 trace，且 `langfuse.session.id` 有值
- [ ] 含隐私数据时设 `trace-io-enabled=false`
- [ ] 配 `detail-retention-days`，并真的安排清理任务

**验收**：`ai_run.session_id`、`subject_id`、`cost_cny`、`quality_label` 都有值（不是全 NULL）。

---

## 8. 评测（建议做）

- [ ] 用 `ai_golden_case` 灌 10 条起步用例（六层各来几条）
- [ ] 跑一次，把通过率记成基线
- [ ] 上线前跑 `non-regression` 闸门
- [ ] 线上点踩集中的问题补进黄金集

**验收**：黄金集报告里每条用例的 `failReason` 能指向具体维度（工具没命中 / 条数不对 / 没反问）。

---

## 9. 上线前自查

| 检查项 | 为什么 |
|---|---|
| `trace-io-enabled` 与合规要求一致 | 原文进 trace 是数据留存问题，不是性能问题 |
| Milvus `collection` 已改名 | 默认名是通用的，会和同实例的其他系统串 |
| `max-sessions-per-owner` 合理 | 太小用户建不了会话，太大会被刷 |
| `max-steps` 有上限 | 防模型绕圈烧钱 |
| `timeout-seconds` 与上游网关一致 | 比网关短会白白丢掉还活着的请求 |
| 告警真的在响 | `ai_obs_queue_depth` 查不到时告警是静默失效的 |

---

## 10. 反模式（见过就会踩）

**① 在 Controller 里拼历史、写消息**
业务逻辑漏到了不该在的层，第二个入口（IM / 定时任务）出现时会复制一遍，然后两边行为不一致。
所有入口都走同一个 Facade。

**② 把 `namespace` 放进请求体**
等于把分区隔离的钥匙交给客户端。改一个字段就能读到别人租户的数据。

**③ 会话读写不在同一个锁里**
两个请求各读一份历史、各自追加，库里出现两条互不知情的回答，用户看到的是「它忘了我说过什么」。

**④ 用 `rows=0` 表示「这个工具不产出行」**
空结果率会永远算错，R7 规则误报，最后没人看这个指标。

**⑤ 每轮钩子里做逐工具校验**
模型一轮可能调 3 个工具，钩子只跑一次——漏两个。逐工具的判定只能放 `ToolInterceptor`。

**⑥ 在提示词里手写工具清单**
和代码里的白名单必然漂移。运行器会拼，不要手写。

**⑦ 配置类 `@Component` + `@EnableConfigurationProperties` 一起用**
容器里两个同类型 Bean，启动直接失败（`required a single bean, but 2 were found`）。
