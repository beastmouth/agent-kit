# 10 · 上下文压缩接入

> **状态：已落地（v0.1.0，2026-11-19），默认关闭。** 代码位置见 §4；配置见 §5；基线实测见 §6。
> 决策背景（为什么不上 `HarnessAgent`）见 [08-引擎选型 §5](08-引擎选型.md)。
>
> **一句话结论**：机制建好了、验证过、也实测过——但在当前业务形态下（8 轮 × ~1.25k tokens）
> 开启它是负数收益：命中率 83% → 63%，input token 反增，工具轮延迟 +3.6s。
> 所以它的定位是「异常回合的保险丝」，不是日常路径。数据见 §6.2。

---

## 1. 结论与边界

**不引入 `agentscope-harness`，不迁 `HarnessAgent`，不碰 `AgentState` / `AgentStateStore`。**

只从 harness 的设计里移植三件事，做成脚手架自己的扩展点：

| 移植什么 | 解决什么 | 落点 |
|---|---|---|
| 对话摘要压缩 | 长会话只能被 `history-limit` 硬截断，前缀信息永久丢失 | 引擎侧，`toMessages` / 拼 `messages` 之前 |
| 工具结果截断 | 单条工具结果撑爆上下文 | `ToolBridge` 出口 + legacy 结果回灌处 |
| 上下文溢出兜底 | 模型报 `context_length_exceeded` 时整轮直接失败 | `AgentScopeEngine` catch 内强制压缩重试一次 |

**不移植的**：workspace 文件树、`MEMORY.md` 双层记忆、plan mode、sandbox、声明式 subagent。
前两项与本仓库「MySQL 是唯一真相 + Milvus 向量记忆」直接冲突，后三项当前业务用不上，
且会让 `Agent` / `ToolRegistry` / `ToolInterceptor` 这套契约重写——违反 AGENTS.md 的
「契约优先于实现」与「自定义实现零框架改动」。

## 2. 为什么不能照抄 harness 的 `CompactionMiddleware`

这是本文最关键的一条，不搞清楚会白写。

`HarnessAgent` 的压缩改的是 `AgentState.contextMutable()`——它假设**状态由框架持有**：
框架从 `AgentStateStore` 读回上下文，压缩后写回，下一次 call 继续从这份状态接着跑。

本脚手架是**无状态调用**：每轮从 MySQL 读 `history-limit` 条，`AgentScopeEngine#toMessages()`
转成 `List<Msg>` 后整份传给 `reactAgent.stream(...)`。模型看到的就是我们传进去的那份列表，
`AgentState` 上的改动**不会传到模型**。

框架暴露的可改切面（`agentscope-core-2.0.4`，`javap` 实测）：

```
MiddlewareBase:
  onAgent(Agent, RuntimeContext, AgentInput, next)          // AgentInput(List<Msg> msgs)
  onReasoning(Agent, RuntimeContext, ReasoningInput, next)  // ReasoningInput(List<Msg>, tools, options)
  onActing(Agent, RuntimeContext, ActingInput, next)        // ActingInput(List<ToolUseBlock>) —— 工具执行前
  onModelCall(Agent, RuntimeContext, ModelCallInput, next)
  onSystemPrompt(Agent, RuntimeContext, String)
```

所以：

- **能改上下文**的钩子是 `onAgent`（整轮入口）与 `onReasoning`（每次模型调用前）；
- `onActing` 是**工具执行前**，拿不到结果 → 工具结果截断不能放在中间件里，必须在
  `ToolBridge` 返回处做（那是我们自己写的桥接器，天然可控）；
- `AgentState` 那条路对本仓库无效，别照着 harness 抄。

**结论**：压缩做成引擎侧组件（对 `List<ChatMessage>` 生效），而不是框架中间件。
好处是 legacy / agentscope 两套引擎共用同一份实现——中间件方案只有 agentscope 能用。

## 3. 核心设计：前缀指纹冻结 + 逐字复用

### 3.1 先说清楚在优化什么

DeepSeek 一类服务的前缀缓存按**前缀完全匹配**计费，命中价约为未命中的 1/50。
现有 `prompt-order=v2` + `PromptTailMiddleware` 已把日期/记忆压到尾部，实测第二轮命中 73.5%。

**压缩是唯一会主动破坏这个前缀的操作**：摘要一旦变化，它后面的全部内容作废。
所以压缩方案的评价标准不是「省了多少 token」，而是「每破坏一次缓存，换回来多少 token」。

### 3.2 错误做法（照抄 harness 的默认行为）

每次超过阈值就重新调一次 LLM 生成摘要 → 摘要文字变了 → 前缀全废 + 每轮多一次 LLM 调用。
在长会话里这会形成「越压越贵」的反向螺旋。

### 3.3 正确做法：摘要按前缀指纹冻结

摘要的版本号不是时间、不是轮次，而是**被压缩前缀的内容指纹**
（`SHA-256(role + NUL + content ...)` 取前 16 位十六进制）。三条不变量：

1. **同指纹逐字复用**：同一指纹下，摘要文本从缓存读，**不重新生成**。
   字节级一致才能让前缀继续命中。
2. **只在跨阈值时升版**：尾部再长到阈值才生成新指纹。此时前缀本来就要变，
   一次性失效是必要成本，摊到 N 轮上可以接受。
3. **结构固定**：压缩后的列表永远是 `[一条摘要消息] + [尾部原文 N 条]`，
   摘要在最前、条数固定为 1，不随轮次抖动。

### 3.4 状态机

```
轮 1..k    累计未超 trigger        → 原样传，不压缩，缓存不动
轮 k+1     超 trigger              → 生成摘要 v1(指纹 f1) → 缓存 → [v1] + tail(8)
轮 k+2..m  前缀仍覆盖到 f1 的内容  → 复用 v1 正文（零 LLM 调用）→ 前缀逐字一致 → 持续命中
轮 m+1     尾部再长到阈值          → 生成 v2(指纹 f2) → 覆盖缓存 → 一次性失效
```

平均成本：每 N 轮一次 LLM 摘要调用 + 一次前缀失效，换回「上下文不再无限增长」。

### 3.5 为什么不用 messageId 做版本号

原本打算用「覆盖到哪条消息」的 messageId 作版本，实现时否掉了，两个原因：

1. `sessionId` 在 `ChatEngine#handle` 的冻结契约里**不存在**，为压缩改契约的代价远大于收益；
2. 消息 ID 是雪花、不连续，无法从「窗口里第 k 条」反推 ID。

内容指纹恰好就是「前缀是否完全一致」的判定标准，比 messageId 更贴合目标。
副作用是「内容相同的两段前缀可跨会话复用摘要」——这没有语义问题（输出只取决于输入），
隔离键（`RunContext.subjectId()`）仍会把不同调用方分开。

### 3.6 摘要写的什么

`SYSTEM_PROMPT` 固定五条要求，其中最重要的一条是：

> 历史里助手声称「已完成」但没有任何工具执行痕迹的，写成「助手声称已完成（未见工具执行记录）」。

压缩是有损的，假回执一旦被压进摘要，后面每一轮都会读到它，比原始对话里的假回执更难纠正。

## 4. 已落地的改动

### 4.1 新增（`agent-kit-core`，`com.beastmouth.agentkit.context`）

| 文件 | 内容 |
|---|---|
| `ContextCompactor` | 扩展点接口：`compact` / `enabled` / `retryOnOverflow`，全部可降级 |
| `CompactRequest` | record：`scope`（隔离键）、`history`、`userMessage`、`force` |
| `CompactOutcome` | record：`history` / `summary` / `coveredKey` / `coveredCount` / `reused` / `savedChars` |
| `CompactionProperties` | `@ConfigurationProperties("agent-kit.context.compaction")` |
| `SummaryStore` | 摘要存储接口（`get` / `put`，按 scope + 指纹寻址） |
| `InMemorySummaryStore` | 默认实现，进程内 LRU，`summary-store=memory`（默认）时装配 |
| `LlmContextCompactor` | 默认实现：估算 → 判阈值 → 查指纹 → 复用或生成 → 组装 |
| `ToolResultClamp` | 工具结果首尾截断 + 占位说明，两套引擎共用 |

### 4.2 修改

| 文件 | 改了什么 |
|---|---|
| `agent-kit-memory/.../session/RedisSummaryStore` | 新增，`summary-store=redis` 时装配；读写失败按未命中 |
| `agent-kit-memory/.../support/KitKeys` | 新增 `contextSummary(scope, coveredKey)`，前缀 `agent-kit:ctxsum:` |
| `AgentScopeEngine` | `toMessages` 前压缩；catch 内 `isContextOverflow` 判定后强制压缩重试一次；`buildToolkit` 传截断阈值 |
| `SubAgentRunner` | `messages.addAll(history)` 前压缩（只在入口压一次）；工具结果回灌前 `ToolResultClamp` |
| `ToolBridge` | `toBlock` 对 `summary` 截断，`data` 不动（它进 metadata，不进上下文） |
| `AgentScopeConfig` | 传入 `ContextCompactor`（`ObjectProvider`）与 `CompactionProperties` |

### 4.3 刻意没做的

- **`AgentContextCache.ContextPack` 没加字段**：摘要归 `SummaryStore`，包归包——两者失效条件不同
  （包按 `lastMessageId` 乐观校验，摘要按指纹版本冻结），塞进一个对象会让「包落后就 evict」误伤冻结的摘要。
- **没做「工具结果落盘 + 回读」**：多副本 + 容器无持久盘时，落盘写的是 A 副本的本地盘，
  B 副本回读不到，模型会拿到一个「有路径但读不到」的结果——比截断更糟。所以只做截断 + 占位说明，
  完整内容仍在 `ai_tool_call` 明细里可查。
- **`temperature` 没做成配置**：`ModelProvider#chat` 没有 per-call 参数，温度由渠道自身配置决定。
  放一个配置项但实际不生效，比没有更坏。

## 5. 配置项

```yaml
agent-kit:
  context:
    compaction:
      enabled: false            # 默认关：不配就与现在行为完全一致
      # 8000 是「异常回合保险丝」而非日常路径：实测日常上下文 ~1.25k tokens（§6）
      trigger-tokens: 8000
      trigger-messages: 0
      keep-messages: 8
      max-summary-chars: 1200
      provider: ""              # 摘要渠道 id；空 = 默认渠道
      chars-per-token: 1.7
      summary-store: memory     # 多副本必须 redis
      summary-cache-max: 512
      summary-ttl-seconds: 604800
      unload-threshold-chars: 0 # 0 = 不截断
      overflow-retry: true
```

完整说明见 [07-配置参考](07-配置参考.md) 的 `agent-kit.context.compaction.*` 一节。

| 项 | 缺省行为 |
|---|---|
| `enabled=false` | 压缩器跳过、截断关闭，行为与引入前完全一致 |
| 没有 `ContextCompactor` Bean | 两套引擎按 `null` 处理，直接跳过 |
| `SummaryStore` 缺失 | 每轮重新生成摘要（不缓存），仍能工作 |
| 摘要模型调用失败 | 本轮降级为不压缩，不抛给调用方 |
| `provider` 配错 | 告警 + 退回默认渠道 |

## 6. 基线实测（deepseek-flash，2026-11-19）

不是估算，是走完 `engine=agentscope` + `prompt-order=v2` 全链路的 8 轮真实对话，
从 `ai_llm_call` 与启动日志取的数。样本会话：16 条消息 / 379 字符 / 约 223 tokens 历史。

### 6.1 压缩关闭（当前线上形态）

| 指标 | 实测 |
|---|---|
| ACT 调用 input tokens | 1047 ~ 1456（均值 ≈ 1250） |
| ACT 命中率（稳定态） | **78.5% ~ 87.9%，均值 ≈ 83%** |
| 路由调用 input / 命中 | 421 ~ 496 / 29% ~ 65% |
| 端到端耗时 | 1.5 ~ 5.4 s |

**关键发现：一轮对话的 1250 个 input token 里，历史只占约 223，其余全是 system + 工具 schema + 协议。**
也就是说，压缩能压的那部分本来就只占 18%。

### 6.2 强行触发压缩（`trigger-tokens=100`、`keep-messages=4` 的对照实验）

| 指标 | 关闭 | 开启 | 变化 |
|---|---|---|---|
| 压缩触发次数 | 0 | 4 | — |
| ACT input tokens | 1047 ~ 1456 | 1141 ~ 1593 | **反而 +130** |
| 每轮首个 ACT 命中 | 78.5% ~ 85.1% | **56.1% ~ 67.6%** | **−18pp** |
| 同轮第二步命中 | 83% ~ 88% | 88% ~ 90% | 基本不变 |
| 端到端耗时（工具轮） | 3.7 / 2.6 s | 7.3 / 6.6 s | **+1 次摘要调用** |

三条结论，都是数据直接给的：

1. **历史太短，摘要比原文还长**：把 223 tokens 的历史换成一段 1200 字上限的结构化摘要，
   token 是往上走的。「压缩」在这个体量上是个负数收益的操作。
2. **每轮重写前缀，命中从 83% 掉到 63%**：因为被压缩的前缀每轮都在变（多一条消息就是新指纹），
   摘要必然重生成。这正是 §3 花大篇幅论证的那个坑，实测确认它真的存在。
3. **摘要调用在主链路上**，工具轮的端到端从 3.7s 涨到 7.3s。用户能感觉到。

所以 `enabled=false` 不是「先保守一点」，是这个业务形态下的**正确终态**。

### 6.3 阈值怎么定：8000 是保险丝，不是日常路径

按实测，日常上下文只有 ~1.25k tokens，`trigger-tokens=8000` 有 6 倍余量，正常永远不触发。
这是刻意的：它只在「工具结果很肥」或「history-limit 被调大」的异常回合兜一下，
而不是每天在正常对话上跑摘要。

真要压，该开的不是它，是 `unload-threshold-chars`——大结果才是真凶，见 §4.3。

### 6.4 顺带发现两件事

- **命中率不是稳定的**：基线里有一轮 ACT 命中 0%（前缀未变却全冷）。说明前缀抖动不只来自压缩，
  渠道侧的缓存过期或分片也会造成。复盘命中率时别一口咬定是压缩干的。
- **成本报表此刻全为 0**：`ai_price` 表是空的，`cost_cny` 落库为 0.000000。要看钱得先灌价格，
  在灌之前只能用 token 数说话。

### 6.5 复跑方式

```bash
# 1) 起服务（模型渠道用环境变量，密钥不进文件）
export DEEPSEEK_API_KEY=...            AGENT_KIT_PROVIDER=deepseek \
       AGENT_KIT_ENDPOINTS_DEEPSEEK_MODEL=deepseek-flash
mvn -o -Pexamples -pl examples/agent-kit-example spring-boot:run

# 2) 打 8 轮同样的对话（同一 subjectId，便于事后清理）
curl -s -X POST localhost:18080/demo/chat -H 'Content-Type: application/json' \
  -d '{"subjectId":"baseline-ctx","role":"parent","message":"本月餐饮花了多少钱？"}'

# 3) 取数
select purpose, input_tokens, cached_tokens,
       round(100*cached_tokens/nullif(input_tokens,0),1) hit_pct, duration_ms
from ai_llm_call c join ai_run r on r.id=c.run_id
where r.subject_id='baseline-ctx' order by c.run_id, c.step_seq;
```

对照实验把阈值压到 100 即可复现 §6.2；跑完记得删 `baseline-*` 的会话、消息、`ai_run` 与其子表，
以及 Redis 里 `agent-kit:ctx:*` 的对应键。

## 8. 不做的事（避免下一轮又讨论一遍）

- ❌ 引 `agentscope-harness` 依赖 —— 只为三个特性背一整套 workspace/state 基础设施，不划算；
- ❌ 迁 `HarnessAgent` —— `AgentStateStore` 与 MySQL 会成为双真相，三层租户塌成两层；
- ❌ 用 `MEMORY.md` 文件记忆替代 Milvus —— 关键词扫描打不过语义召回，且丢掉 `SUPERSEDED` 冲突痕迹；
- ❌ 把压缩写成 `MiddlewareBase` 实现 —— 只有 agentscope 引擎能用，legacy 拿不到；
- ❌ 动 `AgentContextCache.ContextPack` —— 失效条件不同，混在一起必然误伤。

## 9. 上线前需要你确认

1. **多副本就必须配 `summary-store: redis`**，否则同一会话换 Pod 会重生成摘要、前缀缓存失效；
2. **摘要渠道选哪个**：`provider` 建议指到便宜且延迟低的渠道，压缩在主链路上，慢渠道会拖首字延迟；
3. **`trigger-tokens` 不再是待定项**：实测日常上下文 ~1.25k tokens，已定 8000（6 倍余量的保险丝）。
   只有当你把 `history-limit` 调大、或工具开始返回大明细时，才需要按新基线重算；
4. **`unload-threshold-chars` 开不开**：开了会截断工具结果，若业务需要模型读完整明细，保持 0。
